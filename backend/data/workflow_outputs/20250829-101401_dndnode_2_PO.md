# 產品負責人（PO）‑ 任務拆解清單  
> 本清單以 **模組／主功能** 分組，並以「使用者註冊（Customer Registration）」作為範例。  
> 每項任務包含：  
> 1️⃣ 任務概述與目的  
> 2️⃣ 明確操作步驟（可逐步勾選）  
> 3️⃣ 驗收標準（具可驗證條件）  
> 4️⃣ 估時（人/日 或 小時）  
> 5️⃣ 前置條件 / 依賴  
> 6️⃣ 產出物 / 提交物（檔案/PR/設定）  
> 7️⃣ 相關檔案位置或模組  

## 1. Customer‑Management 模組  
| 任務編號 | 任務名稱 | 目的 |
|----------|----------|------|
| CM‑001 | **使用者註冊 (Customer Registration)** | 讓新客戶能夠使用電話號碼註冊並自動產生 OTP，完成註冊流程。 |
| CM‑002 | 客戶資料查詢 | 提供客戶查詢其個人資訊及歷史排隊紀錄。 |
| CM‑003 | 客戶資訊更新 | 允許客戶更新姓名、電話、偏好設定。 |

---

### CM‑001 – 使用者註冊  
| 項目 | 內容 |
|------|------|
| **1️⃣ 任務概述與目的** | 新客戶透過手機號碼進行註冊，系統將：<br>① 儲存客戶資料（電話、姓名、註冊時間）<br>② 產生一次性 OTP 並寄送 SMS<br>③ 返回註冊成功回覆（queueId、OTP 失效時間）。 |
| **2️⃣ 明確操作步驟** | ① **前端**: 表單輸入電話、姓名 → 送 POST /api/customers/register <br>② **後端**: <br>   - 驗證輸入格式 (電話 10‑11 位)<br>   - 檢查電話是否已註冊<br>   - 若未註冊：<br>     * INSERT customer<br>     * CREATE OTP (expiry = now+5min)<br>     * CALL SMS gateway (Twilio) → 送出 OTP<br>   - 若已註冊：返回 409 Conflict <br>③ **回應**: 201 Created + { customerId, otpExpireAt } <br>④ **單元測試**: 驗證 OTP 產生、SMS 送出、重複註冊處理。 |
| **3️⃣ 驗收標準** | 1. 輸入合法電話時，返回 201 Created 且 customerId 為 UUID。<br>2. OTP 會於資料庫中存入且 `expire_at` 為 `now + 5min`。<br>3. SMS API 成功回傳 200，且訊息內容包含 OTP。<br>4. 5 分鐘後再次使用相同 OTP 應回傳 400（已過期）。<br>5. 同一電話註冊兩次返回 409。 |
| **4️⃣ 估時** | 3 人日（開發 2 人日 + 單元測試 0.5 人日 + code review 0.5 人日） |
| **5️⃣ 前置條件/依賴** | - PostgreSQL、Redis（OTP 缓存）已建表<br>- Twilio/SMS API 可用（或 Mock）<br>- JWT 身份驗證已完成（註冊不需要登入） |
| **6️⃣ 產出物 / 提交物** | - PR: `backend/customer-service/src/main/java/.../CustomerController.java`、`CustomerService.java`、`OtpService.java`<br>- 測試檔案：`CustomerServiceTest.java`、`OtpServiceTest.java`<br>- 文檔更新：`docs/api.md`、`docs/security.md` |
| **7️⃣ 相關檔案位置或模組** | `backend/customer-service`（Spring Boot）<br>資料庫表：`customers`, `otp_codes`<br>API 端點：`/api/customers/register` |

## 2. Queue‑Service 模組  
| 任務編號 | 任務名稱 | 目的 |
|----------|----------|------|
| QS‑001 | 取號（Create Queue Item） | 客戶在取號機或 Web 端發起排隊，建立 QueueItem 並回傳順序號。 |
| QS‑002 | 叫號（Next Queue Item） | 櫃員從前端發送「叫號」請求，系統決定下一位客戶並推送通知。 |
| QS‑003 | WebSocket 同步 | 建立 WebSocket 連線，持續推送排隊位置與叫號狀態。 |

### QS‑001 – 取號  
| 項目 | 內容 |
|------|------|
| 1️⃣ 任務概述與目的 | 當客戶掃描 QR / 手機輸入服務編號後，建立 QueueItem，並自動產生順序號（seq_no）及預估等待時間。 |
| 2️⃣ 明確操作步驟 | ① 前端送 POST /api/queue/take { serviceId, phone }<br>② 後端: <br> - 檢查 serviceId 存在<br> - 透過 Redis 排行序計數器生成 seq_no<br> - INSERT queue_items (service_id, customer_id, status=WAITING, seq_no, created_at)<br> - 回傳 201 + { queueId, seqNo, eta } |
| 3️⃣ 驗收標準 | - 正常取號回傳 201 且 seqNo 為遞增值。<br>- 若同一服務並行取號，seqNo 不重複。<br>- 預估等待時間正確計算（取決於 queue.length * avgServeTime）。 |
| 4️⃣ 估時 | 2 人日 |
| 5️⃣ 前置條件/依賴 | - Service 表已建立<br>- Redis 已啟動（使用 INCR 命令）<br>- QueueItem 服務已啟動 |
| 6️⃣ 產出物 / 提交物 | - PR: `backend/queue-service/src/.../QueueController.java`, `QueueService.java`<br>- 測試: `QueueServiceTest.java` |
| 7️⃣ 相關檔案位置或模組 | `backend/queue-service`<br>資料庫表：`queue_items` |

## 3. Notification‑Service 模組  
| 任務編號 | 任務名稱 | 目的 |
|----------|----------|------|
| NT‑001 | FCM / APNs 推送 | 當叫號或重要事件發生時，推送通知至客戶手機。 |
| NT‑002 | WebSocket 事件推送 | 即時同步排隊位置、叫號狀態給前端。 |
| NT‑003 | 推送失敗重試機制 | 對 FCM/APNs 失敗事件進行重試並記錄失敗原因。 |

### NT‑001 – FCM / APNs 推送  
| 項目 | 內容 |
|------|------|
| 1️⃣ 任務概述與目的 | 當 QueueItem 變為 CALLED 時，透過 FCM（Android）或 APNs（iOS）推送「已叫號」通知，並回傳成功/失敗。 |
| 2️⃣ 明確操作步驟 | ① 在 QueueService 處理完叫號後，觸發 `NotificationService.sendPush(queueItem)`<br>② NotificationService: <br> - 從資料庫取得客戶 device_token、platform<br> - 使用 `fcm-java` 或 `apns-client` 送訊息<br> - 若成功，寫入 `notification_logs` (status=SUCCESS)<br> - 若失敗，寫入 status=FAILURE 並觸發重試 (最大3次) |
| 3️⃣ 驗收標準 | - 成功推送回傳 200 且日誌顯示 SUCCESS<br>- 失敗時日誌顯示 FAILURE 且重試次數 ≤3<br>- 3 次失敗後仍顯示 FAILURE 且不再重試 |
| 4️⃣ 估時 | 2 人日 |
| 5️⃣ 前置條件/依賴 | - Firebase Project、APNs certificate 已設定<br>- `device_tokens` 表已存客戶設備資訊<br>- NotificationService 已實作重試排程 |
| 6️⃣ 產出物 / 提交物 | - PR: `backend/notification-service/src/.../PushService.java`<br>- 測試：`PushServiceTest.java`、Mock FCM/APNs |
| 7️⃣ 相關檔案位置或模組 | `backend/notification-service` |

## 4. OTP‑Service 模組  
| 任務編號 | 任務名稱 | 目的 |
|----------|----------|------|
| OT‑001 | OTP 產生 & 寄送 | 產生一次性驗證碼，並透過 SMS 寄送給客戶。 |
| OT‑002 | OTP 驗證 | 驗證客戶輸入的 OTP 是否正確、未過期且未重複使用。 |

### OT‑001 – OTP 產生 & 寄送  
| 項目 | 內容 |
|------|------|
| 1️⃣ 任務概述與目的 | 在註冊或驗證流程中，產生 6 位數 OTP，並即時發送 SMS。 |
| 2️⃣ 明確操作步驟 | ① 生成 6 位隨機數（如 482391）<br>② 存入 `otp_codes` (phone, code, expire_at, used_at=NULL) <br>③ 以 Twilio 呼叫 REST API 送出 SMS<br>④ 回傳 200 OK (不含 OTP) |
| 3️⃣ 驗收標準 | - OTP 6 位數字；<br>- expire_at 為 now+5min；<br>- Twilio API 呼叫成功（200 OK）；<br>- 不允許同一電話同時存在多個未過期 OTP。 |
| 4️⃣ 估時 | 1 人日 |
| 5️⃣ 前置條件/依賴 | - PostgreSQL 表 `otp_codes` 已存在<br>- Twilio 服務可用（或 Mock） |
| 6️⃣ 產出物 / 提交物 | - PR: `backend/otp-service/src/.../OtpController.java`, `OtpService.java`<br>- 測試: `OtpServiceTest.java` |
| 7️⃣ 相關檔案位置或模組 | `backend/otp-service` |

# 總結  
1. **每個任務都可獨立開發、測試、review**，不會影響其他模組。  
2. 任務估時以 **人日**（開發＋測試＋review）為單位，方便資源排程。  
3. 所有 PR 必須在 **backend/** 目錄下提交，並同步更新 docs（api, security, ops）。  
4. 若遇到「性能瓶頸」或「安全漏洞」等風險，可於同一架構下快速替換 Redis → Kafka 或 Postgres → CockroachDB，確保 3 個月 MVP 交付。  

> 這份清單可直接交付給開發隊，作為 Sprints 1‑3 的工作項目。祝開發順利，MVP 3 個月內落地！

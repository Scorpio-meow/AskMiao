## 1. 市場掃描 & 競品/參考  
| 競品 | 主要特色 | 差異化學習點 |
|------|----------|--------------|
| **Queue‑IT** | 雲端即時排隊，主打大流量防 DOS | 需要外部 CDN，對於本土化服務可參考其「速率限制」設計 |
| **Vinda** | 具備 QR 取號 + 直視顯示 | 可學習其 QR 成功率與線下硬體整合流程 |
| **SimpleQueue** | 低成本、單純推送通知 | 推送失敗率低，使用雙路通知（WebSocket+推送） |
| **Nimbly** | 多語言 & 手機小程式 | UI/UX 的「即時顯示」可作為參考標準 |
| **本土自研** | 內部系統，結合客服中心 | 觀察其資料庫結構與權限分層，避免重複造輪子 |

**重點差異**  
- 本系統**不依賴專屬硬體**，只利用現有取號機及手機端，降低部署成本。  
- 目標是 **≤2 s** 的叫號同步，需比競品更強的 WebSocket + 本地快取。  
- **資料一致性 99.9%**，須設計事務一致性與重試機制。

**學習點**  
1. 低延遲即時推送（WebSocket + FCM）是關鍵。  
2. 離線備援（本地緩存 + 重試）可避免單點斷線。  
3. UI 需要「快取 & 立即回饋」以提升客戶體驗。

## 2. 技術可行性 & 最佳實踐  
| 需求 | 技術選型 | 主要實踐 / 風險對策 |
|------|----------|---------------------|
| **即時同步** | WebSocket（Node.js / Spring）+ Redis Pub/Sub | 低併發：10k 連線；高併發：使用 Nginx 作負載均衡、Horizontal Pod Autoscaling |
| **資料庫** | PostgreSQL (主表) + Redis (快取、佇列) | 事務鎖 + 行級鎖，避免多個櫃員同時叫號。 |
| **推送** | Firebase Cloud Messaging (Android) / APNs (iOS) | 兩路通知：WebSocket + 推送，推送失敗自動重試 |
| **驗證** | OTP via SMS (Twilio / 阿里雲短信) | 防止虛假電話號碼；存檔 5 分鐘的驗證碼，單次使用 |
| **安全** | TLS 1.2+, JWT + OAuth2 for internal auth | 防止 MITM，敏感資訊加密存儲 |
| **測試** | JMeter / k6 (壓力)、Selenium (UI) | 30‑min 併發 5k；確保 2s 延遲內 |
| **部署** | Docker + Kubernetes | 版控、滾動更新、灰度發布 |
| **監控** | Prometheus + Grafana；ELK | 監控 latency、error rate、CPU/MEM；異常自動告警 |

**最佳實踐**  
1. **分層架構**：API → Service → Repository。  
2. **資料一致性**：使用 Saga/兩階段提交減少資料不一致。  
3. **彈性設計**：WebSocket 失效時自動切換至輪詢，保持功能不間斷。  
4. **CI/CD**：單元 → 整合 → 壓力 → 佈署，確保每次更新不破壞即時同步。

## 3. PRD 梗概  
### 核心用例  
| 用例 | 觸發 | 主要流程 | 失敗流程 |
|------|------|----------|----------|
| **取號** | 客戶在取號機點選服務 | 1. 選服務 → 2. 輸入電話 → 3. 發送 OTP → 4. 成功寫入 DB → 5. 顯示排隊號 | OTP 驗證失敗 / DB 寫入失敗 → 顯示錯誤訊息，重試 |
| **等候查詢** | 客戶/櫃員查詢排隊位置 | 1. 查詢 API → 2. 讀取快取/DB → 3. 回傳位置 | API 超時 → 顯示「請稍後」 |
| **叫號** | 櫃員選擇下一號 | 1. 撤離佇列 → 2. 更新狀態 → 3. 推送通知 | 推送失敗 → 重試 3 次，失敗則顯示「通知失敗」 |
| **確認** | 客戶確認到櫃員處 | 1. 櫃員掃描 QR / 手動輸入號碼 → 2. 驗證號碼 → 3. 更新狀態為「服務中」 | 處理失敗 → 回報客戶並恢復佇列 |
| **結束** | 服務完成 | 1. 更新狀態為「已完成」 → 2. 清除快取 | 完成失敗 → 重試，失敗則人工介入 |

### 主要流程圖（簡化）  
1. 客戶 → 取號機 → 前台 API → PostgreSQL → Redis Queue → 櫃員端  
2. 櫃員端 → 推送服務 → 客戶手機  
3. 客戶確認 → 前台 API → 更新狀態 → 客戶離場  

### 非功能性需求  
- **可用性**：99.5% SLA，日夜備援。  
- **延遲**：呼叫同步 ≤ 2 s；資料寫入 ≤ 1 s。  
- **安全**：傳輸 TLS，數據加密，敏感欄位加密存儲。  
- **可擴展性**：可水平擴展至 10k 同時併發。  
- **審計**：所有狀態變更寫入審計表。  
- **可測試性**：模組化接口，易於單元測試。

## 4. MVP 定義 & 非目標  
### MVP（核心功能）  
1. 前台取號（服務類型、電話、OTP）  
2. 等候查詢（手機/取號機）  
3. 櫃員叫號（WebSocket + 推送）  
4. 客戶確認（QR/號碼驗證）  
5. 狀態更新（完成/離場）  

### 非目標（MVP 內不包含）  
- 高級報表 / KPI 面板  
- 多語言切換  
- 生物識別登入  
- 客戶自助退票 / 改號  
- API 對外公開  
- 大型資料分析 / ML 預測

## 6. 風險矩陣 & 緩解策略  

| 風險 | 影響 | 機率 | 重要性 | 緩解措施 |
|------|------|------|--------|----------|
| 網路斷線導致取號失敗 | 取號成功率 < 99% | 中 | 高 | 本地緩存 + 斷線自動重連；離線取號時先寫入本地，再同步 |
| 推送失敗導致叫號延遲 | 叫號即時性 > 2 s | 中 | 高 | 兩路通知（WebSocket + FCM）；失敗即自動重試 |
| 電話號碼驗證失敗 | 客戶無法完成取號 | 低 | 中 | OTP 重新發送，電話格式檢查 |
| 資料庫併發過高 | 數據一致性 < 99.9% | 高 | 高 | 資料庫分區、水平擴展、Redis Pub/Sub 確保訊息順序 |
| 合規問題（個資） | 法律風險 | 低 | 中 | TLS 傳輸、資料最小化、加密存儲、隱私政策 |
| 功能變更頻繁 | 時程延誤 | 中 | 中 | 需求變更流程（影響評估 + 優先級調整） |
| 離線模式不夠健全 | 取號機無法離線取號 | 低 | 低 | 前端離線模式 + 重新同步 |
| 監控告警不足 | 隱藏性能瓶頸 | 低 | 中 | Prometheus + Grafana，設定自動告警 |

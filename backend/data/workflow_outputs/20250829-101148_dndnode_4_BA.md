## 1. 問題定義與背景  
- **業務痛點**：現場排隊方式繁瑣、客戶等待時間長、櫃員與前台資訊不即時同步。  
- **目標**：打造一套「數位叫號系統」的完整流程圖，將客戶端與櫃員端的交互流程以可視化、可追蹤的方式呈現，確保數據即時一致並提升服務體驗。  
- **範圍**：僅覆蓋取號、等候、叫號、確認、處理、結束等六大功能模組；不涉及硬體（取號機、顯示屏）或外部通信網路設計。

## 2. 目標與成功指標  
| 目標 | 成功指標 | 評估時機 |
|------|----------|----------|
| 取號準確率 100% | 取號成功率 ≥ 99% | 取號機測試完成後 |
| 叫號即時性 | 叫號與櫃員端同步延遲 ≤ 2 秒 | 叫號流程測試完成後 |
| 客戶體驗提升 | 客戶等待時間平均減少 30% | 服務中心 3 個月內 |
| 櫃員工作效率 | 每班次處理客戶數量提升 20% | 服務中心 3 個月內 |
| 數據一致性 | 前台/後台數據一致率 ≥ 99.9% | 數據同步測試完成後 |

## 3. 既有假設與風險  
| 假設 | 風險 | 風險緩解措施 |
|------|------|--------------|
| 前台取號機可連接公司內部網 | 網路斷線導致取號失敗 | 斷線自動重連 + 本地緩存 |
| 櫃員端能即時收到推送通知 | 推送失敗導致叫號延遲 | 兩路通知（聲音 + 手機） |
| 客戶電話號碼可驗證 | 虛假電話號碼 | SMS 驗證碼 |
| 資料庫讀寫速度足以支撐即時同步 | 資料庫併發過高 | 資料庫負載平衡 |
| 服務類型與分流規則已確定 | 需求變更頻繁 | 需求更改流程定義 |

## 4. 關鍵決策點  
1. **資料同步方式**：即時 WebSocket 還是輪詢？  
2. **呼叫通知渠道**：僅手機推送、還是加聲音廣播？  
3. **分流策略**：自動分配還是手動指定？  
4. **身份驗證層級**：電話號碼驗證足夠，還是需要一次性碼？  
5. **UI/UX 重點**：前台簡潔快速取號 vs 櫃員端詳細操作面板？  

## 5. 待確認問題清單（優先順序）  
1. **前台與後台使用的設備**：是否只限觸控式？是否支援多語言？  
2. **取號機硬體限制**：是否有現有 QR 讀取模組？  
3. **數據庫類型**：關聯式還是 NoSQL？需要分區或分表？  
4. **同步延遲容忍度**：業務可接受的最大延遲是多少？  
5. **通知平台**：是否已有推送服務（FCM / APNs）？  
6. **安全要求**：是否需要加密傳輸（TLS）？  
7. **分流規則**：是否有優先級或佇列長度限制？  
8. **多班次管理**：櫃員能否在同一時間段多次登入？  
9. **異常處理**：客戶失聯、手機號碼無效時的流程？  
10. **報表需求**：是否需要即時統計（今日排隊人數、處理時長）？  
11. **可擴展性**：系統預期支援多少同時併發？  
12. **回退機制**：資料遺失時可否快速恢復？  
13. **合規要求**：個人資訊保護法規是否適用？  
14. **部署環境**：雲端、私有雲、或本地伺服器？  
15. **測試策略**：功能測試、壓力測試、用戶測試分工？  

## 6. MVP 粗略範圍  
### 包含（核心功能）  
- 前台取號：選擇服務類型、輸入電話、拍攝 QR、寫入資料庫。  
- 等候查詢：客戶可在手機或前台查看隊列位置。  
- 櫃員叫號：選擇下一號、同步通知（手機推送 + 聲音廣播）。  
- 客戶確認：櫃員驗證號碼、電話、進行業務處理。  
- 狀態更新：完成後更新資料庫，客戶離場。  

### 非目標（未納入 MVP）  
- 高級報表與分析（排隊統計、員工績效）。  
- 多語言支援。  
- 進階身份驗證（指紋/人臉）。  
- 客戶自助退票或改號。  
- API 對外接口。

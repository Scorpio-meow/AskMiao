# ADR-0007: BM25 加入漢字單字與雙字欄位，並以片段層級基準評估檢索

[繁體中文](0007-han-ngram-bm25-and-passage-level-evaluation.md) | [English](0007-han-ngram-bm25-and-passage-level-evaluation_en.md)

## 狀態

已通過 (Accepted) - 2026-11-01

補充 [ADR-0003](./0003-rrf-relevance-citations-and-tool-trust.md) 的 BM25 斷詞與檢索評估。

---

## 背景與問題陳述

1. **評估只有文件層級**：評估工具只計算文件層級的 hit@k 與 MRR。一份檔案切成數千筆記錄的知識庫（例如社群貼文匯出檔），所有片段同屬一個檔案，文件層級指標永遠是滿分，分辨不出排序好壞；專案也沒有內建的標準語料，調整檢索設定時無從比較。
2. **jieba 切錯繁體詞時 BM25 整個漏掉**：jieba 內建詞典以簡體為主，繁體文字常切錯，例如「大眾捷運系統」切成「大眾捷／運系統」、「新臺幣」切成「新／臺／幣」、「喪亡者」切成「喪／亡者」。查詢的切法與文件不同時，詞項完全對不上：實測企業文件語料 BM25 只取回 79% 的正解片段，社群貼文語料只有 65%。
3. **常見調整缺乏本專案的量測**：BGE 查詢指令、RRF 參數、凸組合融合、重排權重、相對門檻等做法各有文獻支持，但沒有在本專案的資料上驗證過。

---

## 架構決策內容

### 1. BM25 另建漢字單字與雙字欄位

- BM25 索引除了 jieba 詞欄位，另建 `han_unigrams`（每個漢字）與 `han_bigrams`（相鄰兩個漢字）。兩個欄位只取漢字連續區段（U+3400–U+4DBF、U+4E00–U+9FFF、U+F900–U+FAFF），不跨標點、英數字與假名。
- 查詢時三個欄位各自產生詞項，全部以 OR 組合，由 Whoosh BM25F 合併計分，三個欄位權重相同（實驗中把字欄位權重降到 0.5 或 0.3 都沒有更好）。
- 依據：中文資訊檢索研究指出，以「詞＋單字」或「詞＋雙字」建索引比單用斷詞穩健，斷詞錯誤時字層級比對仍能補回（Nie et al., 2000；He et al., 2002）。單字欄位補回召回，雙字欄位讓字序相連的片段（「海邊」）排在字散落的片段（「上海…旁邊」）前面。兩個欄位都加在社群貼文語料上最好，在企業基準與只加單字欄位相同。
- `TOKENIZER_RULES_VERSION` 由 2 升為 3。既有 BM25 索引的斷詞簽章因此不符，後端首次啟動時自動依資料庫片段重建 BM25，向量不需重算。

### 2. 片段層級評估與內建基準

- 標準問答集新增選填欄位 `relevant_passages`：列出能代表正解的短原文片段，內容包含任一片段的知識庫片段即視為相關。以原文比對而不記 chunk_id，切塊設定或重建索引後標註仍然有效；片段在知識庫中找不到時評估直接報錯，不會默默算成 0 分。
- 有標註原文片段的題目另計片段層級的 precision@k、nDCG@k、原文片段 recall@k、MRR 與**候選召回**（重排前的候選是否已包含正解）。候選召回低是召回問題（調整 BM25、向量或 `TOP_K`），候選召回高但排名差是重排問題。
- `scripts/evaluate_retrieval.py --corpus 目錄` 以上傳時相同的流程切塊，在暫存 SQLite 與暫存索引上建立知識庫，不連線正式資料庫；`--min-passage-ndcg` 可在指標退步時讓 CI 失敗。
- 內建基準：`backend/eval/corpus/`（12 份虛構的「喵喵科技」企業文件，加上《大眾捷運法》全文作為條文型文件與干擾，共 119 個片段）與 `backend/eval/corpus_golden.jsonl`（103 個正例、15 個反例）。題目刻意包含口語改寫（「外婆過世」對「祖父母喪亡」）、簡體、錯字、英文縮寫、跨文件與新舊版干擾（2025 與 2026 年版差旅辦法）：未指定年份的題目兩版都算相關，指定年份只算該版；反例都是語料確實沒有、但領域相近的問題。測試會驗證每個原文片段都完整落在上傳流程切出的片段內。

### 3. 量測結果

以正式程式碼、與 `.env` 相同的參數（`TOP_K=30`、`RRF_K=60`、`RERANK_TOP_K=50`、`RERANK_WEIGHT=0.85`、`RERANK_RELEVANCE_THRESHOLD=0.02`，重排以 OpenVINO 在 Intel 內顯執行、長度 256）量測；變更前後只差 BM25 欄位。

| 指標（片段層級） | 企業文件基準：變更前 | 變更後 | 社群貼文 2,437 筆：變更前 | 變更後 |
|---|---|---|---|---|
| 候選召回 | 0.971 | **1.000** | 0.924 | **0.937** |
| precision@1 | 0.835 | 0.825 | 0.964 | 0.964 |
| nDCG@3 | 0.892 | **0.897** | 0.927 | **0.932** |
| nDCG@5 | 0.898 | **0.907** | 0.893 | **0.901** |
| 原文片段 recall@5 | 0.937 | **0.956** | 0.417 | **0.421** |
| MRR | 0.888 | 0.889 | 0.982 | 0.982 |
| 反例拒絕率 | 0.133 | 0.133 | 0.667 | 0.667 |

- 社群貼文語料不在版本庫中（使用者自行上傳的資料），題目為 56 個主題查詢與 15 個已核對語料中不存在的反例，相關性以貼文內容是否含同義詞組判定。
- 企業基準前 5 名漏掉正解的題目由 6 題降為 4 題，剩下 4 題的候選召回都是 1.0，屬於重排模型的判斷問題（錯字「特修」、英文「WFH policy」、「統編」等）。precision@1 少了 1 題：個別題目的排名會因 RRF 名次改變而上下移動（企業基準 3 題後退、2 題由找不到變成第 1 與第 3 名），整體 nDCG 上升。
- 2026-11-02 OpenVINO 重排改為依實際候選數送入模型後，以同一基準重測：企業基準片段 MRR 0.892、nDCG@3 0.903、nDCG@5 0.909、原文片段 recall@3 0.947，其餘指標與上表相同（重排分數差異在 0.007 以內，個別題目排名微調）。
- 代價：2,437 筆貼文的 BM25 索引由 4.4 MB 增為 7.4 MB，查詢中位數由 1.0 毫秒增為 2.6 毫秒，與每次約 2.7 秒的重排相比可以忽略；建立索引的時間不變。

### 4. 試過但不採用的做法

在兩份語料上逐項比較，只採用兩份都有提升的做法。下表數字來自實驗工具（與正式流程同樣的模型、參數與片段），precision@k 以 min(k, 正解片段數) 為分母。

| 做法 | 結果 | 不採用的理由 |
|---|---|---|
| BGE 查詢指令（「为这个句子生成表示以用于检索相关文章：」） | 企業基準不變、候選召回 0.966 → 0.956；社群貼文 precision@5 +0.008 | 兩份語料方向不一致；BGE v1.5 官方說明不加指令也可 |
| `RRF_K` 改 20 或 100、加權 RRF、凸組合融合 | 差異都在 ±0.005 內 | 沒有一致的提升。凸組合在文獻中優於 RRF（Bruch et al., 2023），但重排之後差異已被抹平；維持不加權 RRF |
| `RERANK_WEIGHT` 0.7 或 1.0 | 兩份語料都下降 | 維持 0.85 |
| 相對門檻（重排機率低於第一名 × r 的片段截掉，排序截斷的簡化版） | 企業基準 r ≤ 0.2 無變化；社群貼文 r = 0.2 時 precision@5 −0.058 | 短貼文的重排機率差距大，相對門檻會截掉相關片段 |
| 重排輸入長度 512（目前 256） | 企業基準完全相同 | 300 字片段加上查詢沒有超過 256 個 token |
| 重排輸入移除結構化記錄的欄位樣板 | 企業基準 nDCG@5 −0.015，先前社群貼文實驗也較差 | 欄位名稱對重排模型有幫助 |
| `RERANK_TOP_K` 20 | 候選召回 0.966 → 0.950 | 維持 50 |
| 門檻提高到 0.05 或 0.1 | 反例拒絕率上升，但社群貼文 precision@5 由 0.871 降到 0.781 或 0.646 | 短貼文正例的重排機率偏低，見下方「反例拒絕」 |

未評估：Contextual Retrieval（Anthropic, 2024）以 LLM 為每個片段產生一段脈絡前綴，再建立向量與 BM25 索引。它需要對每個片段呼叫一次模型，入庫成本與本機小模型的品質都有疑慮，留待之後以本基準評估。

### 5. 重排模型比較：維持 `bge-reranker-base`

2026-11-02 以同一套流程比較 `BAAI/bge-reranker-base` 與 `BAAI/bge-reranker-v2-m3`（皆以 OpenVINO 在 Intel 內顯執行、長度 256，BM25 已含本 ADR 的漢字欄位），並以 `--relevance-thresholds` 掃描門檻：

| 語料與門檻 | base precision@1 | base nDCG@5 | base 反例拒絕率 | v2-m3 precision@1 | v2-m3 nDCG@5 | v2-m3 反例拒絕率 |
|---|---|---|---|---|---|---|
| 企業基準，門檻 0.01 | 0.835 | 0.922 | 0.067 | 0.874 | 0.907 | 0.667 |
| 企業基準，門檻 0.02 | 0.825 | 0.907 | 0.133 | 0.854 | 0.893 | 0.867 |
| 社群貼文，門檻 0.01 | 0.964 | 0.912 | 0.533 | 0.839 | 0.840 | 0.800 |
| 社群貼文，門檻 0.02 | 0.964 | 0.901 | 0.667 | 0.821 | 0.739 | 0.933 |
| 每次重排耗時（中位數／p95） | 2.75／3.67 秒 | | | 8.61／11.19 秒 | | |

- **文件型知識庫**：v2-m3 的機率分得開，門檻 0.01 時 nDCG@5 與 base 門檻 0.02 相同（0.907），反例拒絕率卻由 0.133 升到 0.667；base 要把門檻拉到 0.3 才有 0.733 的拒絕率，nDCG@5 會掉到 0.836。
- **短貼文**：v2-m3 給短貼文的機率更低，任何門檻下的 precision@1 與 nDCG@5 都比 base 差；只有在反例拒絕率相同（0.8）時略勝（nDCG@5 0.840 對 0.819）。
- **延遲**：模型參數約為 base 的兩倍，Intel 內顯上每次重排慢約 3 倍，Agent 一題常查兩到三次，會多出十幾秒。
- **註記（2026-11-02，OpenVINO 改為可變批次後）**：上表延遲是在每次補滿 50 組的固定批次下量的。改為依實際候選數送出後，以企業基準重跑 base（門檻 0.02）：precision@1 與反例拒絕率不變，片段 MRR 0.889 → 0.892，nDCG@5 0.907 → 0.909。把本基準的 118 次重排（每次 30～50 筆）記錄下來，在同一程序交錯重播：固定批次中位數 2.73 秒、p95 3.39 秒，可變批次 2.46 秒、3.26 秒。另以 352 組樣本交錯實測，10 組 2.83 → 0.51 秒。每種新的候選數第一次出現時要多花約 0.3 秒編譯，所以重新啟動後立刻跑評測，會比穩定狀態慢一些。相隔數小時的量測也受機器溫度影響，不宜與上表直接相比。v2-m3 沒有重測。
- **決定**：預設值維持 `bge-reranker-base`。以文件為主、重視「查無資料」判斷且可接受延遲的部署，可改 `RERANKER_MODEL=BAAI/bge-reranker-v2-m3` 並把 `RERANK_RELEVANCE_THRESHOLD` 調到 0.01 左右，再以自己的問答集校準；更換模型後 OpenVINO 會在 `DATA_DIR/openvino_cache` 另外轉檔（約 1.1 GB，編譯快取再約 1.1 GB）。

## 決定產生的影響與權衡

### 正面影響 (Benefits)

- jieba 切錯詞時 BM25 仍能取回片段，兩份語料的候選召回都上升，企業基準達到 1.0；簡體查詢也能藉繁簡同形的字（如「海边」的「海」）命中部分片段。
- 檢索調整有可重現的片段層級基準，報表能分辨召回與排序問題，CI 可用 `--min-passage-ndcg` 擋下退步。

### 負面影響與挑戰 (Trade-offs & Risks)

- **字層級雜訊**：單字比對會帶進只是用字相同的片段，靠 RRF 名次與重排模型過濾；個別題目的排名會變動。
- **索引較大**：每個漢字與每對相鄰漢字都是詞項，BM25 索引約大七成。
- **反例拒絕仍是弱點，未在本決策解決**：`bge-reranker-base` 對領域相近的反例給分偏高（企業基準反例的最高重排機率中位數 0.12、最高 0.74），短貼文正例的機率又偏低（中位數 0.37），單一門檻無法同時兼顧兩種語料。`RERANK_RELEVANCE_THRESHOLD` 仍須以 `--relevance-thresholds` 依實際資料校準；更換為 `bge-reranker-v2-m3` 的取捨見上方第 5 節。
- **基準的侷限**：企業基準由同一人撰寫文件與題目，雖刻意改寫用詞，仍可能偏向字面重疊；119 個片段的規模也小於實際部署。比較設定時應同時看自己的問答集。

### 升級與回退

- **升級**：沒有新增設定。首次啟動時記錄「BM25 索引的斷詞簽章與目前設定不同」並依資料庫片段重建 BM25（2,437 個片段約 6 秒），向量不需重算。唯讀評估在後端啟動完成重建之前會拒絕執行。
- **回退**：舊版程式讀不到新索引裡的分析器類別，載入失敗後會依資料庫片段重建 BM25，不需手動刪除索引。

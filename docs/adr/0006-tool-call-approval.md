# ADR-0006: 有副作用工具的對話內核准

[繁體中文](0006-tool-call-approval.md) | [English](0006-tool-call-approval_en.md)

## 狀態

已通過 (Accepted) - 2026-09-27

補充 [ADR-0003](./0003-rrf-relevance-citations-and-tool-trust.md) 與 [ADR-0004](./0004-tool-admin-permissions-and-subprocess-isolation.md)：ADR-0003 把「自訂 API 與 MCP 工具的出站請求不受聯網限制約束」列為已知風險，ADR-0004 只限制誰能設定工具；本紀錄處理 Agent 在對話中「呼叫」這些工具的時機。

---

## 背景與問題陳述

1. **提示注入可以驅動有副作用的呼叫**：Agent 依模型輸出決定呼叫哪個工具。知識庫文件、網頁或外部 API 回應中夾帶的指令，雖然被包在 `<untrusted_tool_result>` 內，仍可能誘導模型呼叫 `POST`、`DELETE` 類的自訂 API 工具或會寫入檔案的 MCP 工具。信任邊界只是給模型的提示，不是程式層的保證。
2. **呼叫以操作者的憑證執行**：工具由管理員設定，憑證（API 金鑰、Bearer 權杖、MCP 伺服器的環境變數）屬於操作者。任何能提問的使用者，都能間接讓這些憑證對外部系統做出寫入、刪除或付費操作，而且事後無法撤回。
3. **既有防護只管設定、不管呼叫**：ADR-0004 讓一般使用者無法建立或修改工具，但已啟用的工具對所有使用者的 Agent 一律可用，呼叫前沒有任何人確認。
4. **MCP 工具的行為無法事先得知**：MCP 伺服器在探索時才回報工具清單與參數，後端無法從名稱或方法判斷某個工具是否唯讀。

## 架構決策內容

### 1. 以旗標標記需要核准的工具

- `custom_api_tools` 與 `mcp_servers` 各新增 `requires_approval` 欄位。MCP 以伺服器為單位設定：工具清單會隨重新探索改變，逐工具設定容易遺漏。
- **預設值**：自訂 API 工具依 HTTP 方法決定，`GET`、`HEAD`、`OPTIONS` 為 `false`，其他方法為 `true`；MCP 伺服器一律為 `true`，管理員可逐台關閉。以 OpenAPI 匯入時同樣依方法決定，覆寫既有工具時原本需要核准的維持需要核准；更新時把方法改成會改變狀態的方法、又未明確指定旗標者，自動改為需要核准。
- **既有資料**：`upgrade_schema()` 在啟動時補上欄位並回填，規則同上。

### 2. Agent 暫停，由發問的使用者核准

- `ResearchAgent` 在執行工具前查詢 `requires_approval`。需要核准時，`ToolApprovalBroker` 建立一個綁定發問者 `user_id` 的待核准項目（隨機 `approval_id`），SSE 串流送出 `approval_required`（工具名稱、顯示名稱與參數），Agent 在原地等待。
- 前端在該則回答中顯示確認卡片；使用者的決定經 `POST /api/chat/approvals/{approval_id}` 送回。只有建立項目的使用者能回覆，其他人（含管理員）、已處理或已逾時的項目一律回傳 `404`，不透露項目是否存在。
- 串流送出 `approval_resolved` 後，核准者照常執行；拒絕或 300 秒內未回覆視為拒絕，工具不執行，模型收到「使用者未核准，請改以已取得的資料回答，不要再次呼叫同一工具」的工具結果。
- 沒有可核准的使用者時（`approval_user_id` 為 `None`，例如非互動式呼叫），需要核准的工具一律不執行，而不是自動放行。

### 3. 考慮過但放棄的做法

- **只允許唯讀工具**：直接停用 `GET` 以外的工具最簡單，但會失去建立工單、送出表單等正當用途。
- **由管理員審核佇列**：管理員看不到提問的脈絡，也無法即時回應；真正知道「這次呼叫是不是我要的」的是發問者本人。
- **請模型先以文字詢問使用者**：模型輸出正是提示注入的目標，確認必須由程式強制執行，不能交給模型決定。
- **逐一設定 MCP 工具**：工具清單隨重新探索改變，以伺服器為單位較不會漏設；日後確有需要再細分。

## 決定產生的影響與權衡

### 正面影響 (Benefits)

- **有副作用的呼叫必須經過人**：提示注入無法在使用者不知情的情況下，以操作者的憑證改變外部系統。
- **看得到參數再決定**：卡片列出工具與完整參數，使用者能發現被拼進網址或主體的資料。
- **預設安全**：新建的 MCP 伺服器與會改變狀態的 API 工具預設需要核准，非互動式呼叫一律不執行。
- **可回歸測試**：`backend/tests/test_tool_approval.py` 覆蓋預設值、核准與拒絕、逾時、他人核准、無核准者、中途斷線與既有資料庫的欄位回填。

### 負面影響與挑戰 (Trade-offs & Risks)

- **多一次點擊**：每次呼叫需要核准的工具都要確認，頻繁使用時可能產生「核准疲勞」，使用者不看參數就按下核准。
- **`GET` 不代表無害**：預設不需核准的 `GET` 工具仍可能有副作用，或把資料放進查詢字串送往外部；管理員需依實際行為調整旗標。
- **串流保持開啟**：等待核准時串流最多多開 5 分鐘，期間占用該使用者的一個同時串流名額（每位使用者最多 2 個）。
- **單一行程**：待核准項目存在行程記憶體中。多個 worker 或多台主機部署時，核准請求必須送到持有該串流的行程（例如以黏著工作階段），後端重啟後項目失效。
- **管理員測試不經核准**：`/api/api-tools/{id}/test` 與 MCP 工具測試端點由管理員直接觸發，不需要核准。

### 升級與回退

- 欄位在後端啟動時自動加入並回填，不需手動遷移。升級後既有 MCP 伺服器全部需要核准，使用者第一次會看到確認卡片；管理員可在「AI 工具」頁逐一關閉。
- API 客戶端需處理新的 SSE 事件 `approval_required` 與 `approval_resolved`，並提供核准介面；未處理的客戶端會等到 300 秒逾時，該次工具呼叫視為拒絕。
- 回退時還原程式碼即可，舊版會忽略這兩個欄位。但由新版建立的全新資料庫中，這兩個欄位是 `NOT NULL` 且沒有預設值，舊版新增工具時會失敗；此時請先移除這兩個欄位或給定預設值。
